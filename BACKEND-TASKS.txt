=====================================================================
PEMBAGIAN TUGAS BACKEND - Sistem Mapping, Validasi, dan Labeling Aset
=====================================================================

Dokumen ini turunan dari PLANNING.md (baca dulu) dan disesuaikan dengan
tampilan (frontend) yang sudah jadi. Frontend saat ini masih memakai data
tiruan di lib/mock-data.ts dan state di memori browser. Tugas backend adalah
mengganti itu semua dengan database NeonDB + API sungguhan.

Stack: Next.js 16 (App Router) + TypeScript, NeonDB (PostgreSQL), Telegram
Bot API (notifikasi saja), deploy di Vercel.
Catatan Next.js 16: file middleware bernama proxy.ts, dan params di page
bersifat Promise. Baca node_modules/next/dist/docs/ sebelum menulis kode
yang bergantung pada API Next.js.


---------------------------------------------------------------------
A. ATURAN WAJIB (berlaku untuk SEMUA anggota)
---------------------------------------------------------------------
1. Cek role (admin / teknisi) di proxy.ts DAN diulang di setiap route
   handler / server action. Proxy saja tidak cukup.
2. Semua secret (DATABASE_URL, TELEGRAM_BOT_TOKEN, AUTH_SECRET,
   CRON_SECRET) hanya di .env.local dan Vercel. Jangan di-commit, jangan
   dipakai di komponen client. Sediakan .env.example tanpa nilai.
3. Setiap perubahan REF / STATUS / KONDISI aset WAJIB ditulis ke tabel
   asset_history (termasuk perubahan lewat impor Excel).
4. Pencocokan SN selalu menangani 3 hasil: found, not_found, multiple.
5. Password disimpan sebagai hash. Endpoint cron dilindungi CRON_SECRET.
6. Jangan menambah fitur di luar scope (procurement, keuangan, AI, IoT,
   GPS real-time).
7. Nama kode/variabel/kolom bahasa Inggris, teks antarmuka bahasa
   Indonesia.
8. Branch feature/<nama-fitur>, merge lewat Pull Request, minimal 1
   review dari anggota lain.
9. Jika menemukan hal [TBD], TANYA DULU ke tim. Jangan putuskan sendiri
   (lihat bagian F).


---------------------------------------------------------------------
B. PEMBAGIAN TUGAS PER FITUR
---------------------------------------------------------------------
Dibagi per fitur: pemilik modul mengerjakan database, API, sampai
menyambungkan ke halaman yang sudah ada. Nama anggota masih [TBD].

=== MODUL 1 - FONDASI, AUTH, DAN SISI TEKNISI  (Anggota 1) ===
Paling berat karena jadi dasar modul lain, kerjakan paling awal.

Database:
- Setup NeonDB, koneksi, ORM, dan sistem migrasi (setelah ORM diputuskan).
- Tabel users, technician_areas.
- Seed akun admin dan beberapa teknisi untuk pengembangan.

Tugas:
- Login / logout: POST /api/auth/login, POST /api/auth/logout.
  Password hash, sesi lewat cookie httpOnly.
- proxy.ts: redirect berdasarkan login + role
  (/admin/* hanya admin, /teknisi/* hanya teknisi, /login publik).
- Helper bersama requireRole("admin" | "teknisi") untuk dipakai di semua
  route handler.
- Halaman /teknisi: ambil jadwal teknisi yang login dari database
  (ganti technician-picker / currentTechnician milik mock).
- POST /api/mapping-results: simpan hasil scan (satu baris per scan),
  termasuk label_attached dan ubah mapping_status aset.
- Setup deploy Vercel dan environment variable.

Halaman yang disambungkan:
  /login, /teknisi, /teknisi/kantor/[officeId],
  /teknisi/kantor/[officeId]/chassis/[chassisId]
  (komponen: mapping-provider.tsx, mapping-workspace.tsx,
  chassis-workspace.tsx, chassis-list.tsx, office-list.tsx)

=== MODUL 2 - PENCOCOKAN SN & DATA ASET  (Anggota 2) ===

Database:
- Tabel assets, asset_history (index pada assets.serial_number).

Tugas:
- POST /api/scan/match: cocokkan SN ke EQ. Respons:
    { "result": "found" | "not_found" | "multiple", "assets": [...] }
  Normalisasi SN dulu (trim, uppercase). Logika awal ada di lib/match.ts.
- PATCH /api/assets/[id]: ubah REF / STATUS (dan KONDISI, lihat [TBD])
  + tulis asset_history dalam SATU transaksi.
- GET /api/assets: daftar aset dengan pencarian (EQ, serial number,
  kode aset), filter kantor, dan pagination.
- GET /api/assets/[id]/history: riwayat perubahan aset.
- Impor Excel (fitur "Impor Excel" di halaman Data Aset admin):
    POST /api/assets/import
  Alurnya sudah dibuat di frontend (lib/asset-excel.ts), pindahkan
  logikanya ke server:
    * Kolom: EQ, Jenis (Chassis/Modul), Serial Number, Kode Kantor,
      SN Chassis, REF, Status, Kondisi, Kode Aset.
    * EQ sudah ada -> perbarui aset + catat asset_history.
      EQ baru -> buat aset baru.
    * Validasi per baris, kembalikan daftar baris bermasalah.
    * Modul dihubungkan ke chassis induk lewat "SN Chassis".
    * Hanya admin. Batasi ukuran file.
    * Jalankan dalam transaksi; sebaiknya sediakan mode "dry run"
      untuk pratinjau sebelum benar-benar disimpan.
- Ekspor Excel: untuk dataset besar sebaiknya GET /api/assets/export
  (generate di server, ikut filter pencarian). Versi client yang ada
  sekarang boleh dipertahankan dulu.
- Impor dataset awal EQ-SN (skrip seed sekali jalan / lewat fitur impor).

Halaman yang disambungkan:
  /admin/aset (components/asset-table.tsx), dan bagian pencocokan SN di
  halaman teknisi (bersama Anggota 1).

=== MODUL 3 - JADWAL, MONITORING & NOTIFIKASI  (Anggota 3) ===

Database:
- Tabel offices, mapping_schedules, notification_logs.

Tugas:
- CRUD jadwal: GET/POST/PATCH/DELETE /api/schedules. Aturan yang sudah
  ada di frontend dan HARUS diulang di server:
    * tanggal wajib diisi dan tidak boleh sebelum hari ini,
    * satu kantor tidak boleh punya dua jadwal aktif (terjadwal/berjalan)
      di tanggal yang sama,
    * status: terjadwal, berjalan, selesai, dibatalkan,
    * teknisi yang ditugaskan opsional dan harus melayani area jadwal.
- GET /api/offices (dan CRUD kantor bila perlu).
- GET /api/dashboard/progress: progres mapping per kantor
  (sudah / belum / tidak ditemukan).
- Laporan hasil mapping + ekspor (halaman /admin/laporan).
- Telegram:
    * lib/telegram.ts (kirim pesan, token hanya di server),
    * GET /api/cron/notify-schedule  (pagi: jadwal hari ini),
    * GET /api/cron/notify-results   (sore/malam: ringkasan hasil),
    * validasi header CRON_SECRET, catat ke notification_logs,
    * vercel.json untuk Vercel Cron (cek batas frekuensi paket).

Halaman yang disambungkan:
  /admin (progress-dashboard.tsx), /admin/jadwal (schedule-manager.tsx),
  /admin/laporan.

Penguji silang (sesuai PLANNING): Modul 1 diuji Anggota 2,
Modul 2 diuji Anggota 3, Modul 3 diuji Anggota 1.


---------------------------------------------------------------------
C. RANCANGAN DATABASE
---------------------------------------------------------------------
Dasar: PLANNING.md bagian 7, ditambah hal yang sudah dipakai frontend
(chassis/modul, area, status mapping per aset, kode label).
Nama kolom asli dataset EQ-SN masih [TBD]; sesuaikan tabel assets
setelah file dataset dicek. ERD final disepakati bersama di Sprint 0.

users
  id PK, name, username UNIQUE, password_hash,
  role ('admin' | 'teknisi'), telegram_chat_id (nullable),
  created_at

technician_areas            -- teknisi bisa melayani 1 atau 2 area
  user_id FK users, area ('grobogan' | 'solo')   PK(user_id, area)

offices
  id PK, code UNIQUE (mis. KTR-MJS), name, address

assets
  id PK,
  kind ('chassis' | 'module'),
  parent_id FK assets (nullable; modul menunjuk chassis induknya),
  eq, serial_number, ref, status, kondisi, asset_code,
  office_id FK offices,
  mapping_status ('belum' | 'sudah' | 'tidak_ditemukan'),
  label_status ('belum' | 'terpasang'),
  label_code (nullable; kode QR dari label fisik),
  created_at, updated_at
  Index: serial_number, eq, office_id
  UNIQUE: eq   (impor Excel memakai EQ sebagai kunci pembaruan)
  Catatan: serial_number SENGAJA tidak unique, karena satu SN bisa cocok
  ke lebih dari satu EQ (hasil "multiple").

mapping_schedules
  id PK, office_id FK, area ('grobogan' | 'solo'),
  scheduled_date DATE, assigned_to FK users (nullable),
  status ('terjadwal' | 'berjalan' | 'selesai' | 'dibatalkan'),
  created_by FK users, created_at
  Constraint: unique (office_id, scheduled_date) untuk status aktif
  (partial unique index) agar aturan "1 kantor 1 jadwal aktif per
  tanggal" dijaga di level database juga.

mapping_results             -- satu baris per scan
  id PK, schedule_id FK, asset_id FK (nullable bila not_found),
  scanned_sn, result ('found' | 'not_found' | 'multiple'),
  scanned_by FK users, scanned_at, label_attached BOOLEAN

asset_history
  id PK, asset_id FK, field ('ref' | 'status' | 'kondisi'),
  old_value, new_value, changed_by FK users, changed_at

notification_logs
  id PK, type, payload JSON, sent_at, success BOOLEAN

Catatan:
- Gunakan enum atau CHECK constraint untuk kolom bernilai terbatas.
- Perubahan aset + asset_history selalu dalam satu transaksi.
- Tentukan perilaku ON DELETE (disarankan tidak menghapus fisik aset;
  pakai status).

E. URUTAN KERJA
---------------------------------------------------------------------
Sprint 0 (bersama)
  - Setup repo, NeonDB, Vercel. Putuskan ORM dan auth.
  - Sepakati ERD, format respons API, alur Git.
Sprint 1
  - M1: auth + proxy role + tabel users. M2: tabel assets + impor
    dataset. M3: tabel offices + mapping_schedules.
  - Tabel dibuat lewat migrasi, bukan manual di dashboard Neon.
Sprint 2
  - M2: API pencocokan (3 hasil). M3: CRUD jadwal.
  - M1: halaman teknisi membaca jadwal dari database.
Sprint 3
  - M2: ubah REF/STATUS + riwayat, halaman data aset, impor/ekspor Excel.
  - M3: dashboard progres. M1: POST mapping-results.
Sprint 4
  - M3: Telegram + cron + laporan. Integrasi semua modul.
Sprint 5
  - Black-box testing, uji dengan teknisi, SUS, perbaikan, dokumentasi.

Cara menyambungkan ke frontend (berlaku untuk semua modul):
  1. Buat API + uji di Postman.
  2. Ganti impor dari lib/mock-data.ts di komponen terkait dengan
     pemanggilan API / query server.
  3. Hapus komponen demo (components/demo-loading.tsx) dan ganti dengan
     state loading yang asli.
  4. Hapus data tiruan yang tidak terpakai lagi.
  5. Pastikan "npm run build" dan "npm run lint" lolos sebelum PR.

Catatan teknis Next.js 16 (cacheComponents aktif): jangan memanggil
new Date() / Date.now() saat render di komponen yang ikut prerender.
Hitung di event handler / useEffect atau bungkus dengan Suspense.
